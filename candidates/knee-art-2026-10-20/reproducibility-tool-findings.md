# Knee candidate deterministic export tools — provisional, not a release gate change

**Scope.** Art-tools lane `.11`; no existing candidate source/GLB/PNG, release, ID, set, art decision, runtime or renderer was rewritten. Both knee-pad and strike-target design approvals remain unanswered. This experiment applies *only* to the original three variants generated by `tools/generate_knee_candidates.py`. The later independent turtle-shell/hover target and segmented pad generators have not been changed; any final selected model must separately pass strict two-build checks. All tool output below is in isolated disposable Cookie `/tmp` roots.

## Exact observed failure and causal diagnosis

Two pre-fix clean Blender 4.0.2 builds (`/tmp/aerobeat-knee-candidates-seeded-{a,b}`) differed in **3/3 GLBs, 16/16 PNG files and 3/3 `.blend` containers**. Previously examined PNG decoded pixels differed in two back views; the rest differed in Blender PNG `tEXt` metadata. Comparing old GLB accessors showed matching POSITION/NORMAL vertices and identical oriented triangle **multisets**, but UV-sphere triangle INDEX *order* differed. `tools/blender_scene_fingerprint.py` showed old source scenes had equal objects, materials and vertex positions but different UV-sphere edge, polygon, loop, UV and triangle order; topology was equal as a set. That is the source of geometric export ordering drift, not merely GLB JSON metadata.

Blender native `.blend` save is also not byte-stable: decompressed old pad files had the same 1,203,180-byte length but ~73,670 bytes differed, including nearly every memory-pointer block address and authored mesh ordering. After face ordering was corrected, Blender still embeds run-dependent native pointers, so the source *container* is not an appropriate bitwise build authority. The pre-existing `blender_scene_fingerprint.py` is a semantic check and does not weaken the strict runtime GLB or review PNG byte gate.

## Minimal source fix and prior failed attempts

`tools/knee_mesh_order.py` reauthors the same primitive faces in stable vertex-index order before source save/export, keeping the same positions, face winding, polygon materials, smoothing and procedural UV corners. No vertices are merged. `tools/knee_png_metadata.py` strips **only** Blender's volatile `File`, `Date`, `RenderTime`, `cycles.ViewLayer.total_time`, `cycles.ViewLayer.render_time` PNG `tEXt` keys, with CRC verification and all IDAT/other chunks left intact. A standard-library helper fixture tests precise filtering, idempotence and corrupted-CRC failure. Previous fixed Cycles seed and disabled TEXCOORD export alone could not stabilize Blender's primitive face order; avoiding whole-file checks concealed image metadata but not mesh BIN changes. This fix does not edit pre-existing candidate art or release bytes.

Strict finalized-release two-build GLB/PNG bytes **remain binding**; a final chosen model must also validate semantic source identity and strict manifests before release. There has been no release or art approval.

**Unknowns.** Other Blender hosts, later candidate generators, and native renderer visual parity were not tested. Face ordering uses mesh material/smoothing/UV support exercised by these three candidates only; do not assume arbitrary layered attributes are preserved by this helper. If a selected later model has colors/custom normals/shapekeys, extend the source-safe attribute mapping or choose a narrower deterministic primitive authoring path after demonstrating its need. Normalization deliberately does not strip all ancillary PNG metadata; unexpected new volatile keys should fail the existing byte gate rather than be silently ignored.
