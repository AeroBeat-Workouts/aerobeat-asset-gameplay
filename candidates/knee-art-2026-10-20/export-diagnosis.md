# Read-only diagnosis: repeated provisional Blender exports

**Exact observed failure.** Two fresh Blender 4.0.2 runs of `tools/generate_knee_candidates.py` on Cookie in separate `/tmp/aerobeat-knee-candidates-seeded-{a,b}` roots yielded different SHA-256 bytes for all three GLBs, 16 PNGs, and three Blender files. The open-prong GLB changed length (63,708 versus 60,404 bytes). These runs used Cycles seed 12; neither failed its per-run structural/hash manifest check. Release reproducibility was **not** passed and was not relaxed.

**Expected.** A future final release needs identical temporary-build GLBs/review bytes and valid editable sources before immutable publication; provisional visual review does not require that gate to be solved first.

**Execution path and evidence.** The generator builds primitive Blender meshes, saves `.blend`, exports selected meshes through Blender glTF, renders Cycles PNGs, and hashes each build's outputs. Parsing the two glTF containers shows pad and chevron have *identical JSON* and binary lengths but different BIN payloads. For the pad, 9,138 BIN bytes differ, principally INDEX accessors (six) and a few NORMAL bytes; for chevron, 3,263 bytes differ, principally two INDEX accessors. Open-prong has different accessor/bufferView JSON, length, and BIN contents. Thus **GLB differences are geometric mesh/index-buffer serialization, not timestamps or JSON/container metadata**. Accessor order and index remapping may reflect equivalent surfaces, but no semantic mesh equivalence or glTF pixel parity was proved. PNG chunks contain differing `tEXt` metadata; decompressed IDAT pixel bytes agree on **14 of 16** images. Pad back (7 decoded bytes) and open-prong back (12 decoded bytes) differ slightly even after metadata is removed. This is not solely PNG metadata. `.blend` bytes differ; source semantic scene fingerprint was not measured here. A separate new shell candidate initially exported an unexplained `Cube` with `[-1,1]` bounds under factory startup; inspection found the unremoved default startup object. The new generator explicitly clears startup objects before authoring. This was a candidate-specific geometry bug, not an explanation of differences between the older two clean builds (their generator already clears objects).

**Most likely cause (hypothesis, not proof).** The Blender mesh conversion/glTF export path may traverse or deduplicate coincident primitive vertices/faces with nondeterministic ordering, explaining INDEX changes and occasionally open-prong accessor-count differences. Fixed Cycles seed did not stabilize that path. The small handful of render-pixel changes could reflect nondeterministic render evaluation or mesh order. Alternatives: near-equal float normals, multithreaded Cycles scheduling, glTF exporter vertex deduplication; a clock-only/PNG-metadata-only explanation is contradicted by different GLB BIN bytes and two decoded images.

**Why earlier attempts failed.** Fixing the Cycles seed and disabling texture coordinate export addressed plausible render/UV variance but did not make geometric BIN buffers equal. Comparing only whole-file hashes could not distinguish metadata from geometry and pixels; the chunk/accessor inspection above does.

**Unknowns and minimal reproduction.** Exact Blender internal cause, source-scene semantic equality, geometric equality under index renumbering, and real renderer appearance are unknown. Reproduce by running the committed candidate generator twice in new empty directories on Cookie Blender 4.0.2, then compare GLB BIN and accessor data rather than only hashes. Blender builds on another host were not tested.

**Proposed verification/future corrective action.** After human visual approval, compare source-scene semantic fingerprints and canonicalized per-primitive triangles with normals/material roles across two clean builds; also compare render decoded pixel arrays after stripping PNG ancillary chunks. If the authored meshes differ, identify the responsible mesh conversion/normal step and stabilize it. If only vertex/index ordering differs, canonicalize export ordering without changing topology, then rerun the existing two-build byte gate. Do not replace or weaken that gate on this diagnosis alone. This work intentionally stops at diagnosis to keep the new visual option reviewable.

Problem: Two clean candidate exports differ in GLB/PNG/Blender bytes.

Root cause: Not conclusively isolated; GLB geometric BIN serialization differs, beyond metadata.
Evidence: Identical pad/chevron JSON with different INDEX/NORMAL BIN bytes; differing open-prong accessor lengths; 14/16 PNG decoded images equal and two differ by 7/12 bytes.
Failed approaches: Fixed Cycles seed and disabled glTF TEXCOORD export did not restore identical bytes.
Corrective action: Defer pipeline change until semantic mesh comparison proves ordering vs authored-geometry changes.
Verification test: Two fresh clean builds, canonicalized mesh/material/normal equality plus existing full byte gate.
Related files/components: `tools/generate_knee_candidates.py`, Blender 4.0.2 glTF exporter/Cycles renderer, provisional candidate GLBs/PNGs.
Remaining uncertainty: Exact nondeterministic Blender stage; whether source scene geometry itself differs.
